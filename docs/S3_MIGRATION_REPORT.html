01

What changed, in one paragraph

Media upload now runs through one storage backend that writes to S3 when AWS_S3_MEDIA_BUCKET is set and to local disk otherwise — so nothing changes for local development, and switching to S3 in production is an environment-variable change, not a code deploy. Every uploaded image is re-encoded to WebP and size-capped before storage. Large videos can go browser → S3 directly via a presigned URL, bypassing the backend's own bandwidth. The database gained an additive media_key column for a future vendor-neutral pointer, without touching the URL columns every existing query already reads. Two CLI scripts handle historical migration and cleanup, both dry-run by default and safe to re-run. The India/International market resolver and lead-distribution engine were audited and found already correct — they were not touched.

Every one of these is optional. Unset, the app behaves exactly as it did before this work.

VariablePurpose

07

Remaining AWS setup manual

Nothing below was created — this environment has no AWS account access. Everything above is ready to point at it the moment it exists.

  • S3 bucket, Block Public Access ON
  • CloudFront distribution with Origin Access Control (OAC)
  • Bucket policy granting that OAC read access
  • ACM certificate + DNS for media.panditsuggest.com
  • CloudFront custom origin header set to match ORIGIN_SHARED_SECRET
  • Security group restricting the origin to CloudFront's IP range
  • EC2 IAM role scoped to s3:PutObject/GetObject/DeleteObject/HeadObject on this bucket only

Full detail, including why each step matters, is in docs/S3_CLOUDFRONT_MIGRATION.md.

09

Deployment order

  1. Provision AWSBucket, CloudFront, OAC, DNS — the checklist above.
  2. Deploy this code with the S3 variables still unsetZero behaviour change — confirms the deploy itself is healthy before anything else moves.
  3. Run the database migrationnpm run db:migrate
  4. Set AWS_S3_MEDIA_BUCKET / MEDIA_CDN_BASE_URLNew uploads start going to S3 from this point.
  5. Migrate historical mediaDry run, review the output, then --execute in batches.
  6. Lock the origin downSet ORIGIN_SHARED_SECRET; restrict the security group to CloudFront's IP range.
  7. Clean up, once production has proven stablenpm run media:cleanup — never before.
10

Rollback

A config change, not a data recovery

Unset AWS_S3_MEDIA_BUCKET / MEDIA_CDN_BASE_URL and new uploads go straight back to local disk. Rows already migrated keep their CDN URL — still resolvable as long as CloudFront and DNS stay up. No script here ever deletes a database row, and local files are never removed until media:cleanup is run explicitly.

11

Scoped out, on purpose

  • Multi-size responsive images (320/640/1280 srcset). One optimized WebP per upload instead — three objects per image would touch the schema and every image call site for a further optimization on top of the one that matters most.
  • A frontend "media URL" helper. Not needed — the backend already returns a fully resolved URL, and no frontend code was composing one by hand.
  • Entity-ID-nested S3 keys (pandits/{id}/profile/…). Kept flat by content type — equally secure, and nesting would have meant reordering route middleware for an organisational-only win.
  • Wiring the admin UI to the new presigned-upload endpoints. The backend capability is real and tested; a presigned-URL flow is exactly the kind of thing that silently breaks against real infrastructure (CORS, clock skew) in ways this environment can't catch without a live bucket.
