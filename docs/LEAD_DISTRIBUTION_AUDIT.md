# Lead Distribution Engine — Audit

**PanditSuggest / PanditConnect** · 14 August 2026

This document exists so that someone who did not write the engine can decide
whether to trust it — and so that a pandit who asks *"why am I not showing
up?"* gets a real answer rather than an assurance.

It is in three parts:

1. **The process** — every stage a request passes through, with the file and
   function that performs it.
2. **The scenarios** — the same stages traced with real numbers, generated by
   running the code.
3. **Findings and limits** — what this audit checked, what it found, and what
   it does *not* prove.

Everything in Part 2 is machine-generated:

```bash
cd backend
npm run trace:distribution            # readable in a terminal
npm run trace:distribution -- --md    # this document's Part 2
```

The trace uses a fixed clock and a fixed synthetic population, so the numbers
below reproduce exactly on any machine. **An audit trace you cannot reproduce
is an anecdote.**

## Part 1 — The process

### What the engine promises

> **Fair opportunity, not equal leads.**

The distinction is the whole design. We cannot promise equal leads because the
devotee chooses, and two pandits given identical visibility will not receive
identical contacts if one has a video and three hundred reviews and the other
has an empty profile. What can be promised — and measured — is that inside one
comparable pool, every pandit receives a comparable share of the *chances*.

### The two counters

This is the core idea, and the thing most lead-distribution systems get wrong.

| Counter | Meaning | Written by |
|---|---|---|
| `qualifiedLeads` | Verified devotees who actually made contact | `record_qualified_lead()` (migration 16) |
| `weightedExposure` | Visibility given, weighted by slot position | `recordExposure()` → `POST /pandits/exposure` |

Ranking on **leads alone** is unfair to a pandit shown 500 times who converted
nobody: they look starved, get boosted forever, and keep taking slots from
people who have had no chance at all. Ranking on **exposure alone** ignores the
thing the pandit is actually paying for. Both are required, and Scenario 1 shows
the exposure counter doing precisely this job.

Position weighting matters too. **Slot 1 is worth 7.6× slot 20** (weight 1.000
vs 0.131). Counting raw impressions would treat them as equal and let whoever
sits at #1 accumulate real advantage while appearing equally exposed.

### The pipeline

```
  HTTP request
      │
  ┌───▼─────────────────────────────────────────────────────────────┐
  │ 1. MARKET          browsingMarketFor()          market.js       │
  │    CDN headers only. A client-supplied country is ignored.      │
  └───┬─────────────────────────────────────────────────────────────┘
  ┌───▼─────────────────────────────────────────────────────────────┐
  │ 2. CANDIDATES      fetchCandidates()   distribution.repository  │
  │    Temple × service, with both counters scoped to the market    │
  │    and the rolling window. Correlated subqueries, not joins —   │
  │    a join would fan out and inflate both counts silently.       │
  └───┬─────────────────────────────────────────────────────────────┘
  ┌───▼─────────────────────────────────────────────────────────────┐
  │ 3. ELIGIBILITY     eligibilityFailure()          fairness.js    │
  │    HARD gates, before any scoring. No score rescues a failure.  │
  └───┬─────────────────────────────────────────────────────────────┘
  ┌───▼─────────────────────────────────────────────────────────────┐
  │ 4. PLAN BUCKET     selectBucket()                rotation.js    │
  │    Weighted lottery (default) or strict priority. Seeded on     │
  │    the session, so it is stable for one visitor.                │
  └───┬─────────────────────────────────────────────────────────────┘
  ┌───▼─────────────────────────────────────────────────────────────┐
  │ 5. FAIRNESS SCORE  rankPool()                    fairness.js    │
  │    Computed INSIDE the bucket. Comparing a ₹5,000 pandit's      │
  │    share against a ₹15,000 pandit's would be meaningless.       │
  └───┬─────────────────────────────────────────────────────────────┘
  ┌───▼─────────────────────────────────────────────────────────────┐
  │ 6. ROTATION        selectPage()                  rotation.js    │
  │    Slot 1 pinned to the top-ranked pandit; the rest rotate      │
  │    within a band. Capped pandits held out of the band.          │
  └───┬─────────────────────────────────────────────────────────────┘
  ┌───▼─────────────────────────────────────────────────────────────┐
  │ 7. EXPOSURE        recordExposure()    distribution.repository  │
  │    Only what the client reports as actually rendered.           │
  └─────────────────────────────────────────────────────────────────┘
```

### The score

```
score =  qualityWeight × quality
       + fairnessStrength × (leadDeficitWeight × normLead
                           + exposureDeficitWeight × normExposure)
       + coldStartBoost           (new pandits, bounded twice)
       − overPenalty              (step at 3× fair share)
       + noise                    (seeded jitter, tie-breaks only)

capped pandits: score − 1000, and held out of the rotation band entirely
```

Deficits are **normalised against fair share**, so `+1.00` means "received
nothing" and `−1.00` means "received double", whether the pool has 7 pandits or
500. Without normalising, a large pool would have deficits so small that
fairness would quietly stop working at scale — a failure that produces no error
and no symptom until someone measures the distribution.

### Where each rule is enforced

| Rule | Enforced in | Why there |
|---|---|---|
| Market entitlement | `eligibilityFailure()` | A hard gate, so no score can surface a ₹5,000 pandit to an international visitor |
| Country resolution | `market.js`, server-side | A client-supplied country would be a free upgrade into the premium pool |
| Lead market (billing) | `record_qualified_lead()` — inside the DB function | Derived from the devotee's **verified phone**, never from IP. The application cannot forge it |
| Seat cap | `trg_enforce_seat_cap` trigger | `current_tier` is written from four places; a trigger covers all of them and any future fifth |
| Config bounds | `set_distribution_config()` | Validating only in React means the API and any script bypass it |
| Exposure dedup | `uq_exposure_session_hour` index | Ten refreshes must not make everyone on the page look over-served |

### What is deliberately *not* enforced in the engine

- **Seat cap never filters the listing.** A pandit above the cap has paid.
  Silently showing them to nobody would be the worst possible behaviour, and
  invisible. The cap stops *selling*, not serving.
- **An unknown market records no exposure.** Charging an impression against a
  market we could not determine would corrupt the very counter that decides who
  is shown next. A wrong number is worse than no number.
- **A recommendation is never a qualified lead.** Impressions, card clicks and
  profile views all produce zero leads. Only `record_qualified_lead()` creates
  one, and only for a phone-verified devotee using call or WhatsApp.

### Stage 3 — plan bucket

```

allocation (INDIA): {"bharat":0.7,"global":0.3}
```

The bucket is drawn from a hash of the session, not a random number, so this visitor gets the same bucket on every refresh — while across many visitors the split converges on 70/30.

### Stage 4 — fairness scored INSIDE the bucket

```
pool size       : 7
total leads     : 55
total exposure  : 399.00
fair share      : 1/7 = 0.143  (14.29% each)
```

Fairness is computed within one plan, never across plans. Comparing a ₹5,000 pandit's share against a ₹15,000 pandit's would be meaningless — they bought different things.

Reading the columns:

- `leadDef` / `expoDef` are deficits **normalised against fair share**, so +1.00 means "received nothing" and −1.00 means "received double". Without normalising, a 500-pandit pool would have deficits so tiny that fairness would quietly stop working at scale.

| 1 | P7 | Naresh Bhatt | 1 | 1.000 |

## Scenario 4 — does the engine actually self-correct?

The claim under test: exposure recorded on one request changes who is shown on the next.

500 visitors, one at a time. After each page renders, exposure is credited at the position weight each pandit received — exactly what `recordExposure()` writes. Nothing else changes. Starting state is the uneven population from Scenario 1.

| P3 | Mahesh Dubey | 3.00 | 345.98 | 342.98 | 228 |
| P7 | Naresh Bhatt | 4.00 | 346.70 | 342.70 | 211 |
| P6 | Mukesh Joshi | 35.00 | 35.00 | 0.00 | 0 |
| P2 | Suresh Tiwari | 39.00 | 263.59 | 224.59 | 0 |

| P4 | Dinesh Mishra | 96.00 | 348.94 | 252.94 | 61 |

The penalty is a **step at 3× fair share**, not a slope. A pandit drifting slightly ahead is handled by the deficit term alone; one genuinely running away with the pool needs a shove, because a linear deficit is too gentle at that distance.

### Daily cap

```
P6 Mukesh Joshi: today 5 / cap 5 → score -999.52 (rank 7 of 7)
```

Scored −1000, so a capped pandit sorts below every uncapped one whatever their quality.

```
capped pandit P6 appeared on 0 of 200 first pages
```

**This is the one defect this audit found.** Ranking last is enough in a 500-pandit pool — rank 500 never reaches a rotation band of 60. It did nothing in a small one: at a six-pandit temple the band covered everyone, rotation shuffled them back up, and the capped pandit was measured on **164 of 200 first pages (82%)**, still collecting contacts after hitting the limit. The cap was not the hard exclusion `fairness.js` claimed it was.

Fixed in `rotation.js` — `selectOrder()` now holds capped pandits out of the rotating band entirely. They are held back rather than dropped: if there are not enough uncapped pandits to fill the page they still appear, below every uncapped one, because an empty listing serves nobody. Five tests pin the behaviour.

The cap is per market, so a Global plan keeps separate India and International allowances.

### Cold start

```
P7 Naresh Bhatt: boost +0.15 → rank 1
```

Bounded **twice**: by age (7 days) and by exposure received (200 weighted impressions). A new pandit needs a chance, not a flood — and a deficit model without this boost would rank them top continuously until they caught up.

## Part 3 — Findings and limits

### Finding 1 — the daily cap was not a hard exclusion (FIXED)

**Severity: high. Found by this audit, not by the test suite.**

`fairness.js` scores a pandit at their daily lead cap `−1000`, and its comment
calls this "a hard exclusion, not a nudge".

It was not. Scoring last is sufficient in a large pool — rank 500 of 500 never
reaches a rotation band of 60 — but does nothing in a small one. At a six-pandit
temple the band covers everyone, the rotation shuffles them, and the capped
pandit was measured on:

```
164 of 200 first pages  (82%)
```

They kept receiving contacts after hitting their limit, which is the exact thing
the cap exists to prevent. The bug was invisible because the code *looked*
correct at the point of scoring, and the failure only appears at a pool size the
tests were not exercising.

**Fixed** in `rotation.js` — `selectOrder()` now partitions capped pandits out
of the rotating band. Measured after the fix: **0 of 200**, in both a 6-pandit
and a 40-pandit pool.

Held out rather than dropped: if there are not enough uncapped pandits to fill
the page, capped ones still appear, below every uncapped one. A devotee finding
somebody beats enforcing a billing cap perfectly. Five tests pin all of this,
including that paging still reaches everyone exactly once.

### Finding 2 — priority mode starves lower plans (BY DESIGN, surfaced)

Scenario 6: in priority mode, 2,000 of 2,000 India visitors go to the ₹9,000
pool. **The 200 Bharat pandits receive nothing.**

This is what a priority ladder does, and it is admin-selectable. It is recorded
here because the consequence is severe enough that it must not be discoverable
only after switching. The admin panel projects it in red before the setting can
be saved, and the trace above quantifies it.

### Finding 3 — the plan ladder is inverted (OPEN — business decision)

Not an engine defect. Arithmetic:

| Plan | Seats | Leads / pandit | ₹ per lead |
|---|---:|---:|---:|
| ₹5,000 Bharat | 200 | 35.0 | **₹143** |
| ₹9,000 Global | 150 | 26.0 | **₹346** |
| ₹15,000 International | 150 | 14.0 | **₹1,071** |

**A ₹9,000 subscriber receives fewer leads than a ₹5,000 subscriber.** 70% of
India traffic across 200 seats is more per seat than 30% across 150.

The engine cannot fix this — no allocation weight will, because the problem is
seat counts. The remedy is fewer premium seats (₹9k ≈ 61, ₹15k ≈ 20), which the
admin panel now models live. Until it is settled, the platform is selling a
worse deal at a higher price.

### What this audit does NOT prove

Stated plainly, because an audit that only lists successes is marketing.

1. **Leads are not proven to even out.** Scenario 4 measures the *exposure*
   counter correcting itself. It does not simulate devotees choosing, so it says
   nothing about whether contacts distribute evenly — that depends on the
   devotee. This is why the promise is fair *opportunity*.

2. **The trace runs on pure functions, not on the database.** The SQL in
   `distribution.repository.js` — the counter subqueries, the market scoping,
   the `Asia/Kolkata` day boundary — is exercised by `npm run verify:wiring`
   against a real database, not here. **Nothing in Part 2 touches Postgres.**

3. **The population is synthetic.** Built to hit every branch, not to resemble
   real pandits. The 120,000-visitor simulation uses 500 realistic profiles;
   neither is real traffic.

4. **No production traffic has been observed.** Every number here and in the
   simulation is modelled. The engine went live in this codebase only recently;
   the honest position is that it is verified, not proven in the field.

5. **The admin panel has been opened but not stress-tested.** Concurrent edits
   by two admins, and the behaviour of the projection under unusual settings,
   have not been exercised.

6. **Exposure depends on the client reporting honestly.** `POST /pandits/exposure`
   is rate-limited, position is derived from array index rather than trusted from
   the caller, and the hourly unique index blunts repeats — but a determined
   caller could still under-report their competitor's exposure by omitting them.
   The blast radius is bounded; it is not zero.

### Recommended next checks

| # | Check | Why |
|---|---|---|
| 1 | `npm run verify:wiring` after every migration | The only thing that exercises the SQL |
| 2 | Re-run `sim:distribution` after any weight change | Gini above ~0.25 means fairness has stopped working |
| 3 | Settle the plan ladder (Finding 3) | Before selling more subscriptions |
| 4 | Re-run this trace after touching `fairness.js` or `rotation.js` | Finding 1 was invisible to the tests |
| 5 | Compare projected vs actual ₹/lead after 30 days of real leads | The first real check on the model |
